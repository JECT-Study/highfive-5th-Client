# JECT-151 공연 관리 권한

기준은 2026-11-28 Notion API 명세의 GET `/api/v1/concerts/{concertId}`,
GET `/api/v1/concerts/{concertId}/lineup`, DELETE `/api/v1/concerts/{concertId}`,
DELETE `/api/v1/concerts/{concertId}/teams/{bandId}` 초안이다.
같은 날짜 Swagger에는 이 GET·DELETE가 없어 네트워크 쓰기 구현은 연결하지 않는다.

## 권한과 진입점

- GET의 `myBandIds`가 비어 있지 않은 참여자는 정보 수정 진입을 유지한다.
- `myPermissions.isHostLeader`만 공연 삭제·밴드 편집을 허용한다.
  `isTeamLeader`는 대표자 채팅 권한이며 주최 권한을 부여하지 않는다.
- 밴드의 `isHost` 또는 공연의 `hostBandId`에 해당하면 빼기를 표시하지 않는다.
  직접 ViewModel 명령을 호출해도 주최 밴드 ID를 막고, 저장소도 다시 검사한다.
- 삭제는 `BEFORE_RECRUIT`·`RECRUITING`만 허용한다.
  판매 중·중지·마감·알 수 없는 상태는 확인 후 삭제 불가 안내를 보인다.
  삭제 버튼 숨김 여부가 초안에서 미결정이므로 기존 Figma 삭제 불가 팝업을 사용한다.
- 쓰기는 확인창 → ViewModel 명령 → Repository 순서다.
  ViewModel은 명령이 진행 중이면 삭제·밴드 빼기 모두 재실행하지 않는다.

공통 선행 JECT-150의 상세 정보 탭에서 참여 밴드 편집과 공연 삭제에 진입한다.
Figma의 원래 공연 삭제 위치는 정보 수정 화면 하단이다. 수정 화면은 형제 티켓
JECT-153이 소유하므로 이 브랜치가 복제하거나 의존하지 않는다.
후속 통합 시 `ConcertDeleteButton`을 수정 화면에 배치할 수 있다.
초대·공고 생성·계좌 주인 지정 및 대표자 채팅의 실제 명령은 각각의 담당 기능에서 연결한다.
이 브랜치는 시안에 없는 진입 버튼이나 빈 관리 화면을 추가하지 않는다.

## fake 상태와 세션

`FakeConcertManagementRepository`는 JECT-148의 공연 조회와 JECT-150의 참여 밴드 조회를
위임받아 같은 인스턴스로 조회·삭제를 처리한다. 참가자 원본을 새로 만들지 않는다.
공연 12의 주최 밴드 3, 합성 참여 밴드 9001만 공통 fixture에서 읽는다.
기본 fixture의 권한 두 개는 계속 false이며, 주최자 검증은 테스트의 별도 fixture로만 한다.

삭제 tombstone과 빠진 밴드 ID는 Provider보다 수명이 긴 세션 저장소에 남는다.
쓰기 성공 후 상세·참여 밴드 Provider를 invalidate해 다시 읽으므로 경로 재진입에도
삭제한 데이터가 되살아나지 않는다. 밴드 빼기 후 합류 팀 수도 다시 계산한다.
`myBandIds`는 참가자 목록으로 사용하지 않는다.

쓰기 ViewModel도 화면보다 긴 세션 수명을 사용한다. 응답 전에 상세를 닫고 같은 공연을
다시 열어도 성공한 쓰기가 새 상세·명단 조회를 갱신한다. 갱신 중에는 성공한 밴드 ID를
목록과 명령에서 제외한다. fake도 마지막 비동기 조회 뒤 권한을 다시 확인하고, 같은
공연·밴드의 동시 삭제는 하나만 성공하도록 변경 시점에 검사한다.
`CONCERT_007`도 갱신 전 같은 ID의 재요청을 막는다. 명단 재조회가 성공해 해당 밴드가
다시 포함되면 임시 차단을 해제한다. 약한 구독을 사용해 화면 밖에서 GET 캐시를 붙잡지 않는다.

앱 조합 계층의 `ConcertSessionScope`가 기존 로그인 세션을 구독한다.
세션 식별값이 바뀌면 새 저장소와 ProviderScope를 사용해 이전 계정의 fake 변경과 늦은 응답을
격리한다. 인증 코드·토큰 저장 방식은 바꾸지 않으며, 토큰은 로그에 쓰지 않는다.
각 scoped Provider는 의존성을 명시해야 하며, 누락하면 하위 스코프 대신 루트 저장소를 읽는다.
Riverpod 3.4.3 공식 문서의 `concepts2/scoping` 원칙에 따른다.
프레임이 바뀌기 전에도 기존 세션 저장소를 즉시 종료해 이전 명령의 결과를 버린다.
확인창·오류 안내는 요청한 상세 인스턴스와 현재 경로에만 속하며, 세션이나 경로가 바뀌면
자신이 연 팝업만 닫는다. 공연 삭제의 `CONCERT_001` 안내 후에는 홈으로,
밴드 빼기의 같은 오류는 이전 화면으로 이동한다.

fake의 변경은 메모리에만 있으므로 앱 재실행 후에는 원래 fixture로 돌아간다.
실 서버의 삭제·알림·대표자 채팅방 퇴장은 아직 검증할 수 없다.
확인창은 초안 문구를 보여 주지만 fake가 실제 알림이나 채팅방 퇴장을 수행하지 않는다.

## 거부 응답

| 코드 | 처리 |
| --- | --- |
| CONCERT_001 | 공연 없음 안내 후 상세에서 나가기. 삭제 성공은 홈으로 이동 |
| AUTH_005 | 권한 없음 안내, 상세를 다시 읽어 권한 갱신 |
| CONCERT_007 | 이미 빠진 밴드 안내, 상세와 참여 밴드 다시 조회 |
| CONCERT_008 | 주최 팀을 뺄 수 없음 안내 |
| CONCERT_009 | 티켓 판매 시작 후 삭제 불가 안내 |
| 네트워크·기타 | 오류 안내, 자동 쓰기 재시도 없음 |

서버가 새 상태를 보내 로컬 상태가 `unknown`이면 삭제를 막고 상태 확인 실패를 안내한다.
이를 티켓 판매 시작으로 추정하거나 서버 오류 코드를 새로 만들지 않는다.
세션 복원이 오류를 포함한 로딩 상태로 재시도될 때도 기존 로그인 경로를 가리지 않는다.

## 확인과 장애 추적

진입점 `concert_detail_view.dart` → `concert_participants_preview.dart`·`concert_delete_button.dart`
→ `concert_management_view_model.dart` → `fake_concert_management_repository.dart` 순서로 읽는다.
권한이 다르면 GET 응답과 `ConcertAccess`를 먼저 확인하고, 변경이 되살아나면
`ConcertSessionScope`의 세 저장소 override와 scoped Provider 의존성을 확인한다.
요청이 중복되면 ViewModel의 `submitting`과 버튼의 비활성을 확인한다.

직접 확인할 때 일반 참여자는 편집 진입만, 주최 fixture는 밴드 편집·빼기·삭제를 확인한다.
주최 밴드에는 빼기가 없어야 하며, 확인창 취소는 목록을 바꾸면 안 된다.
삭제·빼기 뒤 홈으로 나갔다가 다시 열어 데이터가 유지되는지 확인하고,
다른 계정으로 전환하면 이전 fake 삭제가 남지 않는지 확인한다.
사람의 직접 확인과 실제 서버 QA는 자동 테스트 통과와 별개이며 아직 미확인이다.

Layout: 기존 상세의 CustomScrollView가 유일한 본문 스크롤이다.
참여 밴드는 같은 정보 섹션의 Wrap에 표시하고 편집 중에만 각 팀의 빼기를 겹쳐 표시한다.
확인창은 폭 320을 상한으로 가운데 표시하며, 좁은 화면에서는 좌우 토큰 여백 안에서 줄어든다.
색·글자·버튼은 기존 라이트 디자인 시스템을 사용한다. 다크 파일럿을 새로 구현하지 않는다.
