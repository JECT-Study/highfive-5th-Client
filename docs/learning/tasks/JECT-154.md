# JECT-154 내 공연 목록

## 범위와 현재 단계

- 승인 범위: 내 공연·공연 이력, 빈 상태, 실제 공연 상세 이동, 명세 없는 목록의 격리된 fake, 테스트·위젯 캡처·한국어 커밋.
- 제외: 푸시·PR 생성·머지·배포, 마이페이지 프로필·탭 구현, 실제 목록 endpoint 추정.
- 선행: 커밋된 JECT-150만 base로 사용한다. JECT-149·153·151은 별도 조합 사본에서 검증하며 이 브랜치에 복사하지 않는다.
- 현재: 지정된 150 커밋 `b3ea57d` 위에서 154 단독 format·analyze·import·전체 389개 테스트와 Codex R2 승인을 확인했다. 승인된 149 `ac9b584`·151 `ef3944e`의 실제 앱 생성 진입·세션 조합도 통과했다. 153의 최종 쓰기 조합 판정은 승인된 교체 커밋으로 진행한다.
- 사용자의 이해 완료·직접 UI 확인·운영 준비는 확인되지 않았다.

## 흐름과 선택 이유

`app/router.dart`의 마이페이지 → `MyConcertsSection` → `myConcertsViewModelProvider` → `myConcertsRepositoryProvider` → `MyConcertsRepository`.

목록 API 명세가 없으므로 Service나 endpoint를 만들지 않는다. fake는 별도 상세를 복제하지 않고 같은 세션의 `ConcertRepository`에서 카드 값을 만든다. 카드마다 누른 ID의 실제 상세 화면을 연다. `MyPageView`에는 선택형 `activity` 슬롯만 추가한다.

### 목록의 범위와 오류

- 목록 ID 중 `CONCERT_001`(삭제)·`AUTH_005`(비참여)만 개별 제외한다.
- 상세가 반환돼도 `myBandIds`가 비어 있으면 목록에 표시하지 않는다.
- 네트워크·5xx·모르는 오류는 빈 목록으로 숨기지 않고 실패 상태로 전파한다.
- 주소에서 지역을 만들지 못하면 공연장을 쓰고, 둘 다 없으면 장소 미정으로 표시한다.

### 날짜와 이동

- 날짜·시각은 상세 계약의 시간대 없는 서버 문자열을 그대로 보관한다.
- 진행 중/지난 공연 구분은 상세 헤더와 같은 기기 날짜를 사용한다. 오늘·미정은 진행 중, 오늘보다 이전은 이력이다. 목록 API가 정해지기 전까지의 추정이다.
- 진행 중은 가까운 날짜부터, 이력은 최근부터 정렬한다. 자정과 앱 복귀에 다시 읽는다.
- 상세에서 돌아오거나 공연 만들기를 닫으면 목록을 다시 읽는다. 화면이 제거됐다면 `ref`를 사용하지 않는다.
- 149와의 공개 계약은 extra 없는 `context.push<int>(AppRoutes.showNew)`다. 주최 밴드 선택을 우회하거나 목록 fixture를 생성 인자로 전달하지 않는다.

### 세션과 DI

`MyConcertsRepository`를 전역 상세에 묶어 두면 중첩 계정 스코프가 무시된다. 따라서 DI에는 매개변수 factory를 등록하고 연결 Provider가 `ref.watch(concertRepositoryProvider)`로 읽은 현재 상세 저장소를 넘긴다. 154의 Provider·ViewModel에만 `dependencies`를 선언한다. canonical 상세·참여 밴드의 스코프 선언은 151 담당이다.

153과 조합할 때 조회·수정은 한 `FakeConcertEditRepository` 인스턴스를 공유해야 한다. 큰 합성 ID 자체는 서버 쓰기 방어가 아니다. 목록·상세·참여 밴드 fake 세트를 실제 API로 전환할 때 함께 교체한다.

## 검증 근거의 구분

- 코드 사실: Provider에서 현재 상세 저장소를 DI factory로 전달한다. fake에서 확인된 두 오류 코드만 건너뛴다.
- 실제 실행: 수정 전 장소 누락·비참여 노출·생성 복귀·날짜 갱신·확대 글자 넘침을 재현했다. 중첩 계정 스코프에서도 잘못된 목록을 재현했다.
- 실제 실행: 리뷰 회귀 테스트와 중첩 스코프 테스트가 수정 후 통과했다. 데이터·빈 상태 위젯 PNG를 확인했다.
- 최종 커밋 기반 검증·조합 검증의 명령과 결과는 외부 `evidence/JECT-154/` 보고서에 기록한다. 사본의 통과를 실제 worktree 최종 통과로 간주하지 않는다.

## 장애 시 확인 순서와 직접 검증

1. 목록 실패: 해당 상세의 오류 코드가 삭제·비참여인지, 아니면 재시도할 네트워크·5xx인지 확인한다.
2. 다른 계정 공연 노출: 세션 스코프의 `concertRepositoryProvider`와 목록 연결 Provider가 같은 저장소를 보는지 확인한다.
3. 수정한 제목이 목록에 남지 않음: 153의 읽기·쓰기 DI가 같은 fake인지, 복귀 후 재조회했는지 확인한다.
4. 추가 버튼이 홈으로 이동: 149의 extra 없는 `showNew` 진입이 선택기를 여는 버전인지 확인한다.

사용자 직접 확인: 마이페이지에서 각 카드·이력을 눌러 제목을 대조하고 뒤로 돌아온다. 공연 추가에서 밴드 선택 후 취소한다. 계정을 바꿔 이전 계정의 공연이 남지 않는지 확인한다.

## 한계

- 목록 필드·포함 범위·정렬·날짜 구분은 아직 추정이며 PR 초안에 따로 나열한다.
- 위젯 캡처는 fixture 기반이다. 실기기·실계정·실제 목록 API·운영 배포 검증이 아니다.
- 149의 로컬 생성 데이터가 목록 fake의 상세 저장소에 합쳐지는 계약은 아직 없다. 생성 복귀 재조회와 목록 신규 항목 반영은 별개의 계약이다.
