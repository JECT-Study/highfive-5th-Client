# JECT-151 공연 관리 권한

기준: JECT-150 `b3ea57d84f122ce02423636794886ebe6f714f9c`.
요청 범위는 공연 상세의 역할별 제어·밴드 빼기·공연 삭제이며, 형제 티켓 152·153은 포함하지 않는다.
계약과 확인 순서는 [공연 관리 권한](../../api/concert-permissions.md)에 기록했다.

## 선택 이유

- 서버의 `myPermissions.isHostLeader`와 참여 여부를 함께 사용한다.
  일반 참여자의 정보 수정은 유지하고 대표자라는 이유로 주최 권한을 추정하지 않는다.
- ViewModel 명령이 권한·주최 밴드·판매 상태·중복 실행을 다시 검사하고, 저장소가 최종 거부한다.
- 쓰기와 조회 갱신은 세션 수명, 안내와 이동은 요청한 화면 수명에 둔다.
  화면을 닫은 뒤 성공이 와도 재진입한 명단을 갱신하고 이전 화면의 팝업을 새 화면에 띄우지 않는다.
- `ConcertManagementRepository`가 공통 조회 계약을 함께 구현해 앱 조합 계층에서 같은 저장소로 연결한다.
  실제 API 선택은 DI에만 둔다. 기본 권한과 공통 참가자 fixture를 바꾸지 않았다.

Riverpod 3.4.3 공식 문서의 scoped dependencies 원칙과 실제 패키지의 약한 구독 API를 확인했다.
코드에서 확인한 문제는 스코프 의존성 누락·화면 수명의 쓰기 처리·비동기 최종 권한 검사 누락이었다.
자동 테스트 결과와 사람의 이해·직접 확인·운영 준비는 별개다.

## 실행 결과

- 확정 선행 커밋의 영문 검증 사본에 151 델타만 적용했다.
- 공통 `fcntl.flock` 및 지정 TMPDIR 아래에서 분석·import 검사와 전체 396개 테스트를 통과했다.
- 코드 생성 종료 코드 0, 생성 파일 변경 0건이다.
- 실제 상세 라우트의 375·320 폭 위젯 캡처를 저장하고 직접 읽었다.
- Codex 읽기 전용 리뷰 3회에서 확인한 P2와 P3를 수정하고 회귀로 검증했다.
  마지막 수정 뒤 추가 리뷰를 실행했다고 주장하지 않는다.

## 한계와 직접 확인

GET·DELETE는 미배포 초안이라 fake만 사용했다. 실제 삭제 API·알림·채팅방 퇴장은 호출하지 않았다.
삭제는 승인된 상세 정보 탭에 있고, 수정 화면 하단은 형제 티켓 통합 범위다.
추가 초대·공고·계좌·대표자 채팅의 미구현 진입 버튼을 만들지 않았다.
일반 참여자의 수정 이동은 기존 `showEdit` 라우트가 등록된 조합에서 연결된다.

사용자 직접 확인과 실기기 QA는 미확인이다. 일반 참여자·주최 fixture를 나눠 확인하고,
주최 밴드 빼기 불가 → 취소 유지 → 삭제/빼기 뒤 재진입 → 판매·unknown 거부 → 계정 전환 순서로 확인한다.
문제가 있으면 GET 권한, `ConcertAccess`, 명령 상태, DI와 scoped dependencies 순서로 추적한다.
커밋 권한만 승인됐으며 push·PR·병합은 요청 범위에 없다.
